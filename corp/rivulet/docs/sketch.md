# Rivulet Sketch

## 철학

### 스트리밍 아키텍처

> 모든 데이터 처리는 스트림 기반의 처리

통합된 스트림 처리를 통해 다양한 데이터 구조와 기능을 고성능으로 처리할 수 있도록 플랫폼을 구성

기존의 람다 아키텍처는 아래 두 세트 및 3개 레이어로 구성
1. 기존 데이터의 배치 처리를 위한 배치 레이어와 배치 처리된 데이터로 구성된 뷰를 서빙하는 서빙 레이어 한 세트  
2. 실시간 데이터를 처리하여 실시간 뷰를 만드는 스피드 레이어 한 세트  

그리고 나타난 카파 아키텍처는 오로지 스피드 레이어와 서빙 레이어만 존재

결국 차이는 기존 데이터를 다룸으로 발생하는 로직 및 데이터 충돌과 오버헤드, 관리 비용을 줄이고 지속적인 업데이트로 서비스에 사용 가능한 실시간 데이터를 제공함에 초점을 맞춤. 하지만 흘려주는 데이터의 윈도우에 따라 그게 실시간이 될지, 과거 특정 시점이 될지는 유연하게 특정되는 부분.

### 상태 저장

솔직히 이해가 어렵긴 함.

- 개별 이벤트에 대한 결과만 반환하는 건 상태 없음 처리(stateless, 필터와 맵이 그 예)
- 실시간 분석과 복합 이벤트 처리, 이벤트 기반 앱과 같은 유스케이스를 다룰 수 있게 하는 것이 상태 가득 처리(stateful)

플링크는 내부에 체크포인트 기반 관리되는 상태 매커니즘을 제공

1. 키 기반 파티셔닝: 스트림을 각 특정 키로 파티셔닝
2. 키 프로세스 함수: 각 키 별로 독립적인 로직을 수행
3. 키 프로세스 함수 내의 각 키에 대한 상태를 관리
   - 마지막 접속 시간
   - 누적 구매액
4. 이벤트 타이머: 특정 이벤트 시간을 기준으로 미래 특정 시점에 대한 콜백 등록 가능
   - 세션 타임아웃
   - 비활성 사용자 탐지

그래서 이 상태 저장이라는 것이, 결국 일련의 스트림을 수행하고 난 뒤의 결과를 축적한 것으로 보면 되는 것? 그래서 이벤트 기반 어플리케이션 엔진이다?

이 상태는 각 스트림의 결과물이라 볼 수도 있지만, 중간 과정일 수도 있을 듯. 예를 들어, "내가 언제 로그인 했다"는 정보로 "나의 최종 로그인 시각"을 나타낼 수 있지만, 다음 스트림으로 이동하여 "전체 유저 중 마지막 활성 유저의 로그인 시각" 상태를 갱신할 수 있고, 더 나아가서 "현재 활성 유저의 수"를 집계할 수도 있음. 이 스트림들은 독립된 별개 스트림일 수 있지만, 연속된 하나의 플로우일 수 있는 것.

### 분산 런타임

- 잡 매니저: 사용자가 제출한 잡 그래프를 보고 실행 계획으로 변환. 적절히 태스크 매니저에 스케쥴링 및 오퍼레이션을 총괄
- 태스크 매니저: 코그 실행하는 애
- 클라이언트: 사용자의 진입점

근데 현실적으로 rivulet은 구조를 다르게 가져갈 필요는 있을 듯. 최대한 심플하게, NATS와 Kafka의 차이처럼.

`사용자 -> [입력 -> 스트림] * N -> 출력`의 단순한 구조도 고려할 것. 각 단계는 정해진 상태를 갱신 및 저장할 수도 있을 것. 한가지 문제가 될 수 있는 부분은 상태 갱신 시 레이스 컨디션인데, 어떤 걸 원함?  
답은 위에 있는데? 키 기반 프로세싱은 한번에 하나만 할 것. 만약 병렬적으로 수행해야한다면, 키를 분리할 것.

또 다르게 생각해야할 부분이 태스크 매니저가 JVM 우선이고, SQL과 python 정도를 지원하는데, 우린 더 넓게, 하지만 성능도 어느정도 좋게 받쳐줄 수 있어야함.

그리고 데이터 엔지니어가 쓴다고 생각하지말자. 프로그래머가 쓰는 거다. 우리에게 더 익숙한 건 실제 동작하는 코드와 json/protobuf다.

이 상태를 기반으로 한 아웃박스 패턴을 고려할 것. 로그를 남기든 뭘 하든 일단 기록하고, 수행하고, OK하면 다음으로 넘길 것.

## 작동 방식

### API

flink는 기본적으로 API를 제공.
- SQL: ANSI SQL
- Table API: 기존 언어 Java, Scala, Python 사용
- DataStream API: 아마 정형화된 자체 스크립팅
- ProcessFunction: 아마 비정형화된 자체 스크립팅

rivulet은 Table API와 ProcessFunction이 섞인 느낌이 되어야 할 듯.  
SDK를 통해 주고 받아야 할 데이터 구조를 정의 및 실행할 수 있도록 구성.

### 상태 관리

flink는 체크포인트를 사용해서, 전체 흐름에 대한 상태를 추적. 심지어, 어느 메시지까지 처리했는 지도 체크포인트로 파악 가능. rivulet은 미리 기술했듯이 아웃박스 패턴과 유사하게 처리할 예정.

입력과 스트림의 피드백이 반복될 때는 별도의 상태로 동작

- 처리 시간: 연산을 실행하는 장비의 시스템 시간
- 이벤트 시간: 이벤트 자체에 포함된 타임스탬프
- 수집 시간: 이벤트가 파이프라인에 진입한 시간

flink는 이벤트 시간을 사용. 리뷸렛도 그럴 것. 그래서 워터마크로 중복된 메시지가 들어오는 걸 최대한 막고자 함. 근데 워터마크를 쓸거면 수집 시간을 쓰는 게 맞지 않나?
